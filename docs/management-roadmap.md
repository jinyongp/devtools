# 로컬 개발환경 관리 확장 계획

상태: 로컬 관리 기능과 검증 기준. 구체적인 명령은 [프로세스 관리](processes.md), [정리와 보관함](cleanup.md), [관리 API](management-api-contract.md)에 정의한다.

## 목표와 사용 모델

devtools를 현재 컴퓨터의 여러 프로젝트를 관리하는 공통 진입점으로 확장한다. Agent는 비대화형 CLI를 사용하고, 사용자는 dashboard에서 같은 기능을 시각적으로 조작한다. 두 인터페이스는 같은 검증, 저장, 잠금, 상태 전이 규칙을 사용한다.

중앙 관리 범위는 현재 OS 사용자의 모든 profile이다. profile 아래에서 공통 값과 env별 override를 관리하고, 프로젝트 디렉터리와 worktree의 연결을 확인한다. dashboard는 profile과 화면을 선택할 때 해당 범위의 데이터를 계산한다.

프로젝트의 기존 실행 명령은 그대로 활용한다. `devtools.toml`의 이름 명령과 `devtools run -- ...`이 환경변수 주입과 실행의 진입점이 된다. macOS, Linux, WSL에서 같은 사용 모델을 제공한다.

현재 제공하는 기능과 API는 [CLI 계약](cli-contract.md), [task API 계약](task-api-contract.md), [port 계약](port-design.md)을 따른다. 이 로드맵의 관리 기능은 단계별로 구현하고 해당 계약에 반영한다.

## 작업 순서

| 단계 | 결과물 | 완료 기준 |
| --- | --- | --- |
| 1. 관리 API 기반 | 공통 변경 요청과 dashboard 접근 계약 | CLI와 dashboard의 결과·오류·동시 변경 판정이 일치한다. |
| 2. 백업·복구 | 암호화 백업, 복구 미리 보기와 적용 | 격리된 환경에 복구한 데이터가 백업 대상과 일치한다. |
| 3. dashboard 편집 | task/workstream 및 var/sec/env 관리 화면 | 화면에서 변경한 내용이 CLI에 반영되고 기존 상태 전이 규칙을 만족한다. |
| 4. 개발 프로세스 관리 | 백그라운드 실행과 수명 관리 | agent 세션 종료 후에도 관리 대상 서버를 조회하고 종료할 수 있다. |
| 5. 전역 저장소 정리 | 정리 대상 미리 보기와 선택 적용 | 변경된 대상은 재판정하고 실행 중인 자원과 유효한 데이터를 보호한다. |
| 6. 실제 프로젝트 적용 | agent와 dashboard를 함께 사용하는 검증 사례 | worktree 공유, 동시 편집, 재시도, 작업 인계가 실제 개발 흐름에서 성립한다. |

[관리 API 계약](management-api-contract.md)에 공통 요청 규칙을 정의하고, [백업·복구 사용법](backup.md)에 CLI와 복원 범위를 기록한다. dashboard는 작업·값·프로세스·백업·정리 action을 연결한다.

## 1. 관리 API 기반

조회용 dashboard에 명시적인 변경 action을 추가한다. HTTP 요청은 허용된 도메인 작업과 구조화된 입력으로 처리하고, CLI와 공통 작업 로직을 사용한다. 도구별 저장 방식은 해당 데이터의 특성에 맞게 유지한다.

- 변경 요청 ID로 중복 실행과 재시도를 처리한다.
- 편집 기준 리비전을 전달해 오래된 화면에서의 덮어쓰기를 감지한다.
- profile, env, 대상과 변경 범위를 요청과 결과에 명시한다.
- task의 점유·실행 컨텍스트와 인계 규칙을 화면에서도 적용한다.
- `devtools dashboard`가 발급한 인증 링크로 접속한 세션에서 모든 profile의 조회와 관리를 제공한다.
- 삭제·복구처럼 영향이 큰 작업은 대상과 변경 내용을 확인한 뒤 적용한다.
- 변경 이력에는 대상과 결과를 기록하고 secret 값은 제외한다.

접속 인증은 단일 세션으로 통합하고, profile 선택은 관리 대상을 정하는 동작으로 취급한다. 현재의 loopback 접근, Host/Origin 검사, 명시적 bearer 인증과 세션 만료를 변경 API에도 적용한다. 같은 OS 사용자 아래에서 동작하는 agent와 브라우저는 공통 저장소를 사용한다. 작업별 입력·상태 검증, 리비전 검사, 요청 ID로 변경의 정확성과 재시도를 관리한다.

## 2. 백업·복구

전체 저장소 또는 선택한 profile을 암호화해 백업한다. var/sec/env와 task/workstream 기록을 복구 대상으로 삼고, port·디렉터리 연결은 복구 환경에서 유효성을 다시 확인한다.

복구는 profile 전체를 일관되게 복원하며, 새 profile로 복구하는 것을 기본으로 한다. 기존 profile을 교체할 때는 백업 검사, 대상과 충돌 미리 보기, 현재 데이터 백업, 전체 교체, 결과 확인 순서로 진행한다. 다른 컴퓨터에 복구할 때는 프로젝트 경로를 다시 연결한다. port 설정과 연결은 복구 환경에서 재검사하고, 프로세스와 세션은 새로 시작한다.

공개키로 백업을 암호화하고, 별도로 보관한 개인키로 복구한다. Agent는 평상시 공개키만 사용해 비대화형으로 백업을 생성한다. 복구할 때는 개인키 파일 경로를 명시적으로 전달한다.

| 대상 | 보관 위치 |
| --- | --- |
| 원본 데이터 | 기존 devtools 전역 데이터 디렉터리 |
| 암호화된 백업 | 사용자가 지정한 디렉터리. 외장 디스크나 클라우드 동기화 폴더를 활용할 수 있다. |
| 백업용 공개키 | devtools 설정 디렉터리 |
| 복구용 개인키 | 비밀번호 관리자 또는 별도 오프라인 저장소. 복구 시 파일로 제공한다. |

전역 설정에 기본 백업 경로를 저장하고 명령별로 출력 위치를 지정할 수 있게 한다. 개인키는 백업과 별도로 보관한다. 원본과 같은 디스크의 백업은 실수 복구에 활용하고, 디스크 고장에 대비하는 복사본은 다른 저장소에 보관한다.

백업 형식, 일관된 스냅샷 획득과 실패 시 복구 동작은 [백업·복구 사용법](backup.md)을 따른다.

완료 검증에는 정상 복구뿐 아니라 잘못된 키, 손상된 백업, 적용 중 실패, 동시 변경을 포함한다. 실패 후 기존 데이터가 보존되는지 확인한다.

## 3. dashboard 편집

현재 task/workstream 생성·의존성·명세·계획·실행 action과 var/sec/env 편집을 제공한다. Processes는 프로젝트·worktree의 명령과 port 조회 및 실행 수명 관리를 연결하고, Storage & recovery는 암호화 백업·복구와 정리·보관함을 연결한다.

profile을 중심으로 다음 화면을 구성한다.

| 화면 | 관리 내용 |
| --- | --- |
| 개요 | 작업 진행, 실행 중 서버, port, 진단 결과 |
| 작업 | task/workstream 등록·수정, 명세, 의존 관계, 체크포인트 |
| 값 | 공통 값과 env override 비교, var 편집, sec 등록·교체·삭제 |
| 프로젝트 | 연결된 디렉터리·worktree와 사용 가능한 이름 명령 |
| 보관 | 백업과 복구 진입점 |

secret은 입력과 교체를 지원하고 일반 조회에는 키·종류·출처 등의 메타데이터만 제공한다. secret 원문은 HTML, 조회 응답과 변경 이력에 포함하지 않는다.

의존 관계를 변경할 때는 영향 범위를 보여주고 기존 순환 검사와 상태 전이를 적용한다. 사용자의 수동 조작도 task 점유와 실행 컨텍스트 규칙을 따른다. 다른 agent가 점유한 작업은 현재 상태와 인계 동작을 명확하게 제시한다.

동시 편집 충돌, 중복 제출, 세션 만료와 화면 갱신을 검증한다. CLI에서 변경한 내용을 dashboard에서 확인하고 반대 방향도 확인한다.

## 4. 개발 프로세스 관리

task의 실행 기록과 OS 프로세스의 수명을 구분해 관리한다. 기존 `run`의 전경 실행을 유지하면서, 이름 명령을 백그라운드로 실행하고 나중에 다시 관리하는 기능을 추가한다.

- profile, instance, 명령, env와 실행 식별자를 연결한다.
- 시작·상태·종료·재시작을 제공하고 기존 port 할당과 연계한다.
- agent나 dashboard가 종료돼도 개발 서버를 유지하고 실행 상태를 다시 조회한다.
- OS 재부팅 후에는 명시적으로 개발 서버를 시작한다.
- PID 재사용과 자식 프로세스를 고려해 종료 대상의 동일성을 확인한다.

동일한 `profile + instance + 이름 명령` 조합은 하나만 실행한다. 같은 조합에 다른 env로 시작을 요청하면 충돌을 알리고 명시적인 재시작으로 변경한다.

재시작은 저장된 실행 대상에 현재 설정과 var/sec를 다시 적용한다. 실패하면 종료 상태와 원인을 기록한다.

기본 화면과 실행 기록은 상태·종료 코드·원인을 제공한다. 진단 메타데이터에는 자식 프로세스의 원문 출력을 포함하지 않는다. 원문 로그 수집은 명시적으로 켤 수 있으며, 수집한 로그에는 용량과 보존 기간 제한을 적용한다. 상태 메타데이터 조회와 로그 원문 조회를 구분한다. 원문에는 자식 프로세스가 출력한 secret이 포함될 수 있으므로 접근과 보존을 상세 계약에서 다룬다.

검증에는 agent·dashboard 종료 후 실행 유지, OS 재부팅 후 상태 판정, 비정상 프로세스 종료, 동일 명령의 동시 시작과 env 충돌, port 충돌, 최신 설정을 적용한 재시작과 프로세스 동일성 판정을 포함한다. 로그 수집의 기본 비활성 상태와 명시적 활성화, 용량·보존 기간 제한도 확인한다.

## 5. 전역 저장소 정리

만료된 조회 캐시는 자동으로 정리한다. 작업 기록·백업·프로젝트 연결은 정리 후보와 영향을 먼저 계산한 뒤 확인한 항목을 적용한다. 적용할 때는 대상의 현재 상태를 다시 검사한다.

- 만료된 조회 캐시는 자동 정리하고 종료된 프로세스 기록은 정리 후보로 제공한다.
- 사라진 worktree 연결과 남은 port 할당을 확인한다.
- 완료된 작업은 보관·내보내기를 통해 관리한다.
- 백업은 보존 정책에 따라 정리한다.

단순 경로 부재와 일시적인 접근 실패를 구분한다. 미리 보기 이후의 상태 변경, 실행 중 자원, 다른 profile에 대한 영향을 검증한다.

## 6. 실제 프로젝트 적용과 검증

하나의 실제 프로젝트에서 agent와 dashboard를 함께 사용한다. 환경변수 주입, 여러 서버 실행, worktree별 port, 작업 인계, 백업과 복구를 연결해 개발 흐름을 확인한다.

구현 단계에서는 변경된 기능의 관련 테스트를 먼저 수행하고, 의미 있는 기능 단위가 완성되면 Docker에서 설치된 바이너리로 통합 검증한다. HOME과 XDG 경로는 격리된 시험 환경을 사용한다. dashboard 변경에는 실제 브라우저의 인증·편집·갱신 검증을 추가한다.

보안 검토는 변경된 권한, 저장, 실행 경로에 집중한다. macOS/Linux 빌드 검사와 실제 OS 실행 검증의 결과를 구분해 기록한다. 커밋은 동작 단위로 나누고 각 단위의 계약, 구현, 관련 검증을 함께 유지한다.

## 구현과 검증 결과 — 2026-09-06

관리 API, 암호화 백업·복구, dashboard 편집, 프로세스 수명 관리, 저장소 정리와 통합 사용 흐름을 구현했다.

- Go 1.27.1의 전체 race 테스트와 vet를 통과했다.
- macOS/Linux의 amd64·arm64 실행 파일을 패키징했다. 실제 OS 실행 검증은 macOS 26.6.2 arm64와 Linux arm64 Docker에서 수행했다.
- 설치된 실행 파일로 backup, bootstrap, cleanup, doctor, install, ports, processes, tasks, workflow의 9개 시나리오를 통과했다.
- workflow는 격리된 Git 프로젝트와 두 worktree에서 task 인계·완료, 서로 다른 서버 port, 다른 profile의 URL 주입, dashboard 백업·복구, worktree 정리와 보관함 복구를 확인한다.
- 브라우저에서 이름 명령 조회·시작·종료, 정리 후보 선택·보관·복구, 암호화 백업 생성과 복구 미리 보기·적용을 확인했다. 연속 확인창이 내용을 유지하는지도 검증했다.
- macOS에서는 주소별 포트 점유 감지와 서버 종료 직후 포트 재사용을 race 테스트로 확인했다. 설치된 실행 파일의 전체 9개 시나리오도 통과했다.

`just verify-docker`로 전체 설치 검증을 실행한다. `just verify-docker workflow`는 통합 사용 흐름을 실행한다. macOS 호스트에서는 [설치 실행 파일 검증](../docker/README.md)의 `--releases` 실행 방법을 사용한다. WSL의 실제 OS 실행 검증은 별도 환경에서 수행할 수 있다.

## 프로세스 준비 확인 확장

사용법과 API는 [프로세스 준비 확인](process-readiness.md)에 정의한다.

1. `project`가 검사 명령과 제한 시간을 검증한다.
2. `runCommand`가 선택한 설정을 전달하고, supervisor가 준비된 환경과 함께 보관한다.
3. supervisor의 인증된 검사 요청이 제한 시간·직렬 실행·종료 처리를 맡는다.
4. CLI check·wait와 Dashboard가 같은 검사 경로를 사용한다.

  macOS/Linux amd64·arm64 배포 빌드 통과.
