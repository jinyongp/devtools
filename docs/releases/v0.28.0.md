# v0.28.0 배포 준비

[문서 목록](../README.md) · [개발·게시 절차](../development.md#릴리스)

v0.28.0 후보는 v0.27.0 이후의 로컬 var/sec 저장·실행 보호를 포함한다.
Windows 네이티브 지원과 CLI protocol v7은 유지한다.
최종 버전은 게시 직전 `release:plan`으로 다시 확인한다.
2026-10-20에는 이 명령이 GitHub 응답 크기로 `ENOBUFS`를 반환했다.
공개 안정 태그 `v0.27.0`의 후보 포함 여부와 이후 feature 커밋을 같은 계산 규칙으로
별도 확인해 `0.28.0`을 얻었다. 오류가 계속되면 [수동 버전 확인](../development.md#릴리스)을
거친 뒤 아래 명시 workflow 입력을 사용한다.
이 문서는 게시 준비와 인계 절차다. 준비 완료나 `publish=false` 검증은 실제 게시를 뜻하지 않는다.
정확한 후보 SHA·workflow 실행·배포물 checksum은 최종 커밋의 검증 기록과 게시 실행에서 확인한다.
workflow의 `notes: standard`는 커밋에서 릴리스 노트를 만들며 이 파일을 자동으로 복사하지 않는다.

## 변경 요약

- secret을 로컬 암호화하고, macOS Keychain·Windows 사용자 DPAPI·기존 Linux Secret Service로
  키를 보호한다. keyring 없는 환경은 명시 passphrase backend와 재사용 세션을 제공한다.
- profile/env 전체 선택을 유지하며, 선택적으로 var/sec 공통 bundle을 한 번 저장해 반복 사용한다.
  `values inspect/uses`로 원문 없이 선택과 실제 전달을 구분한다.
- 실제 실행 입력을 기존 앱 중지 전에 고정하고, 새 non-TTY stdout·stderr와 capture의
  전달된 secret을 기본 마스킹한다. TTY·바이너리 raw 예외는 별도로 선택한다.
- 값 변경은 기본 알림으로 표시한다. `values_update = "restart"`로 선택한 managed 서버만
  자동 교체하며, 실패·결과 불명·반복 재시작 제한은 수동 확인을 요구한다.

## 기존 사용자의 변경 사항

실행 파일 업데이트만으로 기존 평문 secret을 전환하지 않는다. 같은 저장소의 writer를
함께 업데이트하고, 전환 전 암호화 백업·복구 키를 보관한 뒤 [vault 설정과 전환](../secret-protection.md#기존-저장소를-전환하기)을
수행한다. `vault init`은 해당 데이터 root의 모든 profile을 전환한다. 잠금과 암호 만료 뒤의
명시 해제 외에는 기존 키 세션을 재사용하므로 명령마다 암호·키 목록을 입력하지 않는다.
원래 dotenv·입력 파일·과거 로그는 지우지 않으며 전환된 저장소의 in-place downgrade는 지원하지 않는다.

기본 마스킹은 [출력 보호](../output-protection.md)를 따른다. 바이너리 stdout을 사용하는
명령은 `stdout = "raw"` 등 명시 정책을 확인한다. raw 출력에도 capture 저장은 마스킹한다.
잠금은 기존 앱에 이미 전달한 환경을 회수하지 않는다. 저장 성공·새 실행의 전달·readiness·
외부 인증 성공은 각각 확인한다. secret을 포함한 profile 전송의 대상에서도 vault를 준비한다.

macOS는 기존 앱별 Keychain 접근 보호를 유지한다. 서명이 바뀌어 OS 승인이 필요하면
`devtools vault unlock --interactive`를 사용한다. 앱 전체에 읽기 권한을 주는 ACL로 바꾸지 않는다.
production Developer-ID 서명·공증은 이번 검증의 보장에 포함되지 않는다.

## 확보한 검증과 남은 배포 확인

[var/sec 최종 리뷰](../var-sec/Z01-final-review.md)와 [검증 색인](../var-sec/README.md)에
단위·통합·OS별 근거를 연결했다. [전체 Actions 39286793430](https://github.com/jinyongp/devtools/actions/runs/39286793430)은
소스 `1e4bebd6d955ff58409416fea77e8a4183b81253`, `publish=false`,
`system_network_smoke=true`의 최종 재실행 기준 필수 26개 성공, 게시용 3개 skip이다.
처음 실패한 ARM64 위 x64 PowerShell 설치 검사는 같은 소스로 재실행해 통과했다.

공개 [v0.27.0](https://github.com/jinyongp/devtools/releases/tag/v0.27.0)은 baseline
`89100eb98888895a450b2ebd403e4e1c9b5f52d2`이며 vault 기능을 포함하지 않는다.
구현 마감 커밋 `8763df2fe3a7e607ad8c676331c577c0d2bc9c3f`까지 제품 실행 코드는
위 native 검증 소스와 같다. 이후 문서·Skill·검증 도구 결과를 과거 Actions에서 실행한 것으로
표시하지 않는다. 실제 게시에는 아래 절차로 최종 source/version을 고정하고 workflow를 실행한다.
이미 통과한 비게시 검증은 게시된 설치물·Homebrew·Pages의 성공을 대신하지 않는다.

지원 목표는 Windows 11 25H2·26H2의 x64·ARM64이며 최신 누적 업데이트를 전제로 한다.
Actions의 x64는 Server 2025 테스트 호스트, ARM64는 Windows 11이다. Server는 제품 지원 OS가 아니다.
Windows 10은 지원하지 않는다. 실제 PC의 UAC·브라우저 신뢰·터미널 닫기·사용자 설치 관찰,
최종 제품의 WSL2↔Windows 브라우저 네트워크와 전체 OS×CPU 조합은 미검증이다.
외부 provider 계정/LAN과 ARM64 native Chromium도 검증 범위에 넣지 않는다.
상세 조건은 [Windows](../windows.md)·[WSL](../wsl.md) 안내를 따른다.

## 게시 전

1. 문서 변경까지 커밋한 깨끗한 후보에서 `release:plan`이 v0.28.0을 추천하는지 확인한다.
   `ENOBUFS`면 위의 수동 확인으로 버전을 결정하고, 실패한 `release:publish`를 반복하지 않는다.
   다른 안정 버전이 먼저 게시되면 버전을 다시 계산하고 해당 버전으로 검증·패키징한다.
2. 후보 branch와 전체 SHA를 지정해 Release를 `version=0.28.0`, `publish=false`,
   `system_network_smoke=true`로 실행해 disposable macOS/Linux의 OS 변경 검사도 포함한다.
   입력 기본값은 false이며, 아래 명령은 확보한 전체 검증 범위를 유지하도록 true를 명시한다.
3. Windows x64/ARM64 full 제품 검사, macOS/Linux 검사와 package job의 성공을 확인한다.
   필수 실패·누락을 과거 후보의 성공으로 대체하지 않는다. 선택 system-network와 게시 job의 skip은 구분한다.
4. `release-assets`의 여섯 CLI archive·checksum, Skill archive·checksum,
   `install.sh`·`install.ps1`·`version.txt`·LICENSE를 확인한다.
   Windows ZIP은 해당 native job에서 검증한 파일과 동일해야 한다.
5. 최종 커밋의 전체 변경과 최종 리뷰, platform 한계·protocol 변경·복구 조건을 확인한다.
   기존 Windows 구현의 전체 리뷰는 [W9](../windows-support/implementation/W9.md),
   var/sec는 [Z01](../var-sec/Z01-final-review.md), 이후 문서는 [전수 점검](../documentation-audit.md)에 있다.
6. GitHub immutable release 설정, `HOMEBREW_TAP_DEPLOY_KEY` 이름의 secret 존재와
   Pages의 workflow 배포 설정을 확인한다. 2026-10-17 조회에서 기존 안정 release의 immutable=true,
   해당 secret 이름과 Pages build_type=workflow를 확인했다. secret 값의 유효성·tap 쓰기 권한과
   실제 Pages 배포 성공은 각 후속 job에서 확인해야 한다.

## 게시 시

실제 게시는 문서 정비와 별도 작업이다. 게시가 승인된 범위에서만 태그·GitHub Release·
Homebrew·Pages 변경을 실행한다.

승인 후 후보가 원격 main의 ancestor인지 먼저 확인한다. 검증한 커밋을 유지하는 merge라면
그 전체 SHA를 사용한다. squash/rebase로 SHA가 달라지거나 제품·workflow 입력이 바뀌면
새 대상을 다시 고정하고 필요한 gate를 재실행한다.

```sh
git fetch origin main --no-tags
git merge-base --is-ancestor CANDIDATE_SHA origin/main
gh workflow run release.yml --ref main -f version=0.28.0 -f commit=CANDIDATE_SHA -f publish=true -f system_network_smoke=true
```

`CANDIDATE_SHA`는 확인한 40자리 전체 SHA로 바꾼다. 로컬에서 태그를 미리 만들지 않는다.
이 workflow도 필수 검사를 다시 수행하며 성공한 뒤에만 동일 SHA의 v0.28.0 태그와 immutable Release를 만든다.
실제 게시 실행의 배포물은 같은 version/source여도 준비 실행과 별도 job에서 만들어지므로
최종 checksum은 게시 실행 기준으로 다시 확인한다.

## 게시 후

- GitHub Release의 tag·commit·version·여섯 대상과 checksum이 게시 실행의 결과와 일치하는지 확인한다.
- Homebrew job과 installer Pages job을 각각 확인한다. Release 성공만으로 후속 배포 성공을 가정하지 않는다.
  Pages의 `install.ps1`은 게시 태그의 파일과 동일해야 한다.
- 설치기는 v0.28.0을 선택해 version을 확인하고, 업데이트한 CLI의 `version`·`schema`를 다시 조회한다.
  CLI protocol은 7, envelope는 1이며 `devtools.toml`은 versionless다. v6의 run 인자 경계는 유지된다.
- Windows와 WSL은 각각 독립 설치·저장소로 확인한다. 신규 OS UI 검증을 하지 않았다면 미검증 한계를 유지한다.
- CLI와 Agent Skill은 각각 업데이트한다. 실행 중 daemon·dashboard·managed process는 명시 재시작해야 새 실행 파일을 사용한다.

## 실패와 복구

- 필수 검사나 package가 실패하면 태그·Release는 만들지 않는다. 원인을 해결하고 바뀐 후보에서 재검증한다.
- 게시 단계만 실패하면 같은 실행의 실패 job을 재실행한다. 다른 커밋의 태그를 교체하거나 immutable 자산을 덮어쓰지 않는다.
- Homebrew·Pages 실패는 이미 게시된 GitHub Release를 되돌리지 않는다. 해당 후속 job을 재실행한다.
- Windows install/update 중단은 같은 installer 또는 같은 update 입력으로 journal 복구를 재시도한다.
  사용 중 old image와 외부 소유 dvt 파일을 수동 삭제하지 않는다.
- 데이터 저장 형식 전환 후 구버전 binary의 in-place downgrade는 지원하지 않는다.
  이전 CLI로 돌아갈 때는 전환 전에 보관한 호환 backup을 새 데이터 디렉터리에 복원한다.
  실행 파일만 되돌리면 데이터·OS hosts/trust·provider 설정도 복구된다고 가정하지 않는다.
