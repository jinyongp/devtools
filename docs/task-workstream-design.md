# Task와 workstream 설계

상태: task·workstream·dashboard의 사용·API 계약. 실행 예시는 [사용 가이드](tasks.md), 명령별 입력은 바이너리의 `schema`에서 확인한다. [API 상세 계약과 전이 검증](task-api-contract.md)에 입력·출력 필드, action별 전이, 오류·재시도 우선순위와 검증 사례를 정의한다.

## 목적과 합의한 방향

devtools에서 계획 수립부터 실행·검증·마감까지 이어지는 작업 흐름을 관리한다. 단일 `devtools` 에이전트 스킬이 CLI에 저장된 맥락과 상태를 읽고 작업을 진행한다. 기존 workstream 스킬의 명세·계획·검증 연결과 Taskwarrior의 작업·의존성 개념을 통합한다.

macOS, Linux, WSL에서 비대화형 CLI와 JSON 응답을 사용한다. 에이전트가 주 사용자이며 여러 세션의 동시 작업과 세션 중단 후 인계를 지원한다.

| 개념 | 의미 |
| --- | --- |
| profile | 프로젝트를 식별하는 사용자 지정 이름. 같은 profile의 worktree와 clone은 작업 데이터를 공유한다. |
| workstream | 하나의 목표를 달성하기 위한 명세·구현계획·task·검증 근거·결정을 묶는 단위. |
| task | 에이전트가 점유하고 수행하는 개별 작업. profile 안에서 독립적으로 등록하거나 workstream에 연결한다. |
| run | task를 수행하는 실행 시도. 세션이 바뀌어도 저장된 기록으로 추적한다. |
| claim | 작업 선택과 점유를 원자적으로 처리하는 요청. |
| checkpoint | 진행 내용·결정·검증·다음 행동을 복구할 수 있도록 남긴 기록. |

profile별 전역 저장소를 작업 데이터의 기준으로 삼는다. 작업 디렉터리와 실행의 연결도 전역 저장소에서 관리한다.

### 확정: 원본 저장과 공유 범위

CLI가 명세·계획의 Markdown 본문, 구조화된 참조 관계, task와 실행 기록의 원본을 사용자별 devtools 데이터 디렉터리에서 관리한다. 파일은 입력·내보내기에 사용한다. 등록 후에는 저장소의 내용을 기준으로 조회하며 입력 파일의 이후 변경은 명시적인 등록 요청으로 반영한다.

| 환경 | 데이터 디렉터리 |
| --- | --- |
| macOS | `~/Library/Application Support/devtools/data` |
| Linux·WSL | `$XDG_DATA_HOME/devtools`, 기본값 `~/.local/share/devtools` |

Linux·WSL의 XDG 경로가 비어 있거나 상대 경로이면 기본값을 사용한다. 데이터 디렉터리의 `tasks` 아래에서 profile별 action 이력과 요청 영수증을 관리한다.

공유 범위는 현재 컴퓨터의 같은 사용자 계정이다. 같은 profile을 사용하는 여러 저장소·worktree·세션이 같은 명세와 작업 상태를 조회한다. 다른 컴퓨터 간 공유에는 별도의 동기화 계약이 필요하다.

## 계획 편집과 현재 완료 기준

[계획 편집 API](task-edit-api.md)가 원자적 삽입·변경·범위 제외·복원과 실행 기준의 계약이다. lifecycle은 실행·완료 이력으로 유지하고 scope, completion_status, execution_status를 별도로 계산한다. 계획은 실행 중·완료 후에도 저장하며 미완성 coverage는 실행·마감 단계에서 검사한다. 의미 epoch는 단조 증가하고 제목·표시 순서는 의미 기준을 바꾸지 않는다.

저장 v2는 첫 실제 변경에서 baseline과 이벤트를 한 번에 기록한다. 구버전 writer는 v2를 거절한다. 조회·no-op·preview는 업그레이드하지 않는다. 과거 계획은 원자 요청의 마지막 리비전에서 재생한다. backup은 이력을 보존하고 실행 권한을 폐기하며 cleanup은 stale와 모든 running을 보호한다.

## 계획을 workstream으로 관리하기

workstream은 다음 내용을 연결한다.

| 내용 | 작성할 정보 |
| --- | --- |
| 목표 | 달성할 결과, 범위, 적용할 제약. |
| 명세 | 사용자 시나리오, 공개 API, 오류·복구 흐름, 요구사항과 완료 조건. |
| 구현계획 | 설계 선택과 이유, 변경할 영역, 작업 분해, 의존성, 검증 방법. |
| task | 실행할 내용, 관련 요구사항·완료 조건, 예상 변경 범위. |
| 검증 | 확인할 조건, 방법, 결과, 대상 코드 상태와 근거. |
| 연속성 기록 | 결정, 진행 체크포인트, 다음 행동, 인계와 완료 이력. |

설명과 설계는 Markdown으로 충분한 맥락을 담고, 식별자·참조·상태는 구조화해서 연결한다. 입력 파일의 이름은 자유롭게 선택한다.

작은 작업은 목표·완료 조건·task·검증을 간결하게 작성한다. 여러 사용 경로, 영속 데이터, 동시 실행처럼 판단할 사항이 많은 작업은 상세 명세와 복구 조건까지 작성한다.

### 요구사항과 실행의 연결

다음 관계를 기본 모델로 사용한다.

```text
REQ-001  같은 task에 대한 동시 점유 중 하나만 성공한다
  └─ AC-001   두 요청의 결과에 성공한 점유가 하나 존재한다
      └─ task: 원자적 점유 구현
          └─ VAL-001  동시 claim 검증
```

계획의 구현 항목은 task 자체로 관리하고 계획에서는 해당 task를 참조한다. task 상태는 action 이력에서 계산하며 계획 조회에도 같은 계산 결과를 반영한다. ID는 도구가 발급하고 이후 참조에서 유지한다. 위의 REQ·AC·VAL 표기는 설명용이며 실제 식별자 형식은 API 상세화 때 확정한다.

CLI는 참조 대상의 존재, 의존성 순환, 완료 조건과 검증의 연결 같은 구조를 검사한다. 에이전트는 명세의 충분성, 설계의 타당성, 검증 근거가 조건을 증명하는지를 판단한다.

### 계획 변경

확정: 명세·계획에는 도구가 관리하는 리비전을 부여한다. Markdown 본문과 구조화된 참조를 한 요청으로 등록하며, 수정 시 호출자가 읽었던 리비전과 현재 리비전을 비교해 충돌을 검사한다. task와 run에는 작업의 기준이 된 리비전을 기록한다. 새 결정이나 계획 변경 시 영향받는 task와 검증을 확인하고 진행 기록에 반영한다.

기존 실행이 참조하던 내용을 보존하고, 새 실행에는 최신 기준을 제공한다. 변경 충돌 검사에 사용하는 리비전과 사용자 설정 파일의 형식 버전은 별개의 정보다.

변경이 검증에 미치는 영향은 에이전트가 관련 범위와 근거를 확인해 판단한다. 도구는 근거의 기준과 현재 리비전을 비교해 표시하고, 최신 기준에 적용 가능한 결과를 완료 검사에 사용한다.

## 확정: action 이력과 계산된 상태

호출자는 생성·점유·반납·인계·완료·재개 같은 action을 요청한다. CLI가 현재 조건을 확인하고 수락한 action의 적용 기록을 추가한다. 현재 상태는 이 기록과 의존 관계에서 계산한다. 실행 가능 여부는 선행 항목의 현재 완료 여부와 소속 workstream의 실행 조건까지 함께 확인한다.

기록에는 도구가 부여한 순번, 실제 적용 시각, 대상 ID, action 종류, 해당 action의 데이터를 담는다. 같은 시각의 요청이나 시스템 시계 변경에도 적용 순서는 순번으로 결정한다. 동시에 변경될 수 있는 같은 profile의 의존 관계와 점유는 일관된 순서로 판정한다. 순번의 공개 형식과 정확한 적용 범위는 저장 API에서 상세화한다.

완료 시각·점유 시각·최근 활동 시각은 이력에서 도출한다. 완료 후 재개하거나 다시 점유하면 새로운 기록을 추가해 이전 실행과 결과를 보존한다. 빠른 조회를 위한 요약은 같은 이력에서 다시 계산할 수 있는 결과로 관리한다.

### action별 효과

다음 action 이름은 의미를 설명하는 표기이며 최종 이벤트 스키마에서 확정한다.

| action | 기록과 계산 결과 |
| --- | --- |
| `task.created` | task의 목표와 초기 정보를 기록한다. |
| `run.claimed` | 새 run과 점유를 생성한다. 실행 가능한 task에 현재 점유가 있을 경우 요청은 충돌한다. |
| `run.resumed` | 현재 점유 증명을 확인하고 같은 run의 재개를 기록한다. |
| `run.checkpointed` | 현재 run의 진행 내용과 다음 행동을 기록한다. |
| `run.released` | 해당 run의 점유를 반납한다. 다음 실행 가능 여부는 현재 조건에서 계산한다. |
| `run.revoked` | 관리자가 관찰한 run의 점유를 해제하고 사유를 기록한다. 기존 실행 컨텍스트를 무효화하고 task는 open으로 유지한다. |
| `run.taken_over` | 이전 run과 새 run을 연결하고 점유 증명을 교체한다. |
| `task.completed` | 완료 결과와 근거를 기록하고 현재 점유를 해제한다. |
| `task.reopened` | 완료 기록을 보존하면서 task를 다시 작업 대상으로 만든다. 새 점유는 별도 요청한다. |

workstream의 생성·실행 준비·완료·재개도 action으로 기록한다. 취소·대기 사유 변경과 허용 전이는 상세 기본 계약의 상태 규칙을 따른다.

### 원자적 판정

현재 조건 확인과 action 기록은 한 번의 원자적 처리로 수행한다. 두 `claim`이 동시에 들어오면 하나만 점유를 생성한다. 선행 항목 변경과 후행 `claim`도 같은 판정 경계에서 처리해 의존성 조건과 점유 결과가 일치하게 한다.

완료는 결과 기록과 점유 해제를, 인계는 이전 점유 무효화와 새 점유 생성을 각각 함께 적용한다. 거절된 요청은 업무 action을 적용하지 않고 오류를 반환한다. 진단용 실패 기록을 추가하더라도 계산된 업무 상태와 구분한다.

## API 초안

명령은 `devtools task` 아래로 모은다. `--profile` 또는 현재 `devtools.toml`로 프로젝트를 선택한다. task와 workstream은 profile 아래에서 관리하며, env는 변수 주입의 범위로 사용한다.

### workstream과 계획

| 제안 명령 | 동작 |
| --- | --- |
| `task workstream create --title TITLE` | 목표를 관리할 workstream을 생성한다. |
| `task workstream list` | 현재 profile의 workstream을 조회한다. |
| `task workstream show WORKSTREAM_ID` | 목표·단계·진행 상태·다음 행동을 조회한다. |
| `task workstream spec set WORKSTREAM_ID --file FILE` | Markdown 명세를 등록한다. |
| `task workstream plan set WORKSTREAM_ID --file FILE` | Markdown 구현계획을 등록한다. |
| `task workstream context WORKSTREAM_ID` | 명세·계획·결정·현재 작업·검증·다음 행동을 복구용으로 조회한다. |
| `task workstream check WORKSTREAM_ID` | 참조·의존성·필수 근거의 구조적 완결성을 검사한다. |
| `task workstream close WORKSTREAM_ID` | 전체 완료 조건과 필수 검증을 확인해 마감한다. |

명세·계획은 Markdown 본문과 구조화된 참조를 함께 등록한다. 위의 `set --file`을 본문 파일과 결합 입력 중 어떤 형태로 구체화할지는 최종 입력 스키마에서 정한다.

### 작업 등록과 조회

| 제안 명령 | 동작 |
| --- | --- |
| `task add --title TITLE` | 현재 profile에 독립 task를 등록한다. |
| `task add --workstream WORKSTREAM_ID --title TITLE` | workstream에 연결된 task를 등록한다. |
| `task add --file FILE` | 설명·완료 조건·참조를 포함하는 JSON 작업을 등록한다. |
| `task list --workstream WORKSTREAM_ID` | 해당 목표의 작업 목록을 조회한다. |
| `task show TASK_ID` | 작업 상세·의존성·실행·검증 기록을 조회한다. |
| `task next --workstream WORKSTREAM_ID` | 실행 가능한 작업 후보와 선택 이유를 조회한다. |

task는 제목·설명·완료 조건·소속·의존 관계를 관리한다. 입력 필드와 수정·취소·재개 명령은 상세 기본 계약을 따른다.

확정: workstream 연결은 선택 사항이다. 간단한 할 일은 profile 안에 독립 task로 등록하고, 필요할 때 같은 profile의 workstream에 연결할 수 있다. workstream 지정 생략 시 독립 task를 생성한다.

task당 연결할 workstream은 최대 하나다. 연결 변경·해제는 상세 기본 계약의 점유·관계 검사 조건을 따른다.

### 확정: 의존성의 범위

task 간 실행 순서를 제어하는 의존성은 같은 workstream 내부에서 관리한다. CLI는 의존성을 등록할 때 두 task의 workstream이 같은지와 순환 여부를 검사한다. 독립 task들을 의존성으로 묶어 진행하려면 먼저 같은 workstream에 연결한다.

workstream 간 의존성은 같은 profile 안에서 관리한다. 선행 workstream이 모두 완료될 때까지 후행 workstream의 task 점유는 대기한다. 이 기간에도 후행 workstream의 명세·계획 작성과 task 등록은 가능하다. 특정 task를 지정한 `claim`에도 같은 조건을 적용한다.

task와 workstream 모두 여러 선행 항목을 가질 수 있다. 선행 항목 전체의 완료를 요구하는 AND 조건으로 실행 가능 여부를 판단한다. task를 점유할 때는 해당 task의 선행 task와 소속 workstream의 선행 workstream 조건을 함께 확인한다. 선행 항목의 취소는 완료와 구분하여 대기 사유로 표시한다.

두 종류의 의존 관계는 각각 방향이 있고 순환이 없는 그래프(DAG)로 관리한다. 등록 시 범위·대상의 존재·자기 참조·순환을 검사한다. 후행 실행이 시작된 뒤 변경하거나 선행 항목을 재개할 때는 상세 기본 계약의 영향 검사와 반납 규칙을 적용한다.

실행 순서를 강제할 필요가 없는 관련 목표와 결과는 맥락 참조로 기록한다.

여러 작업의 실행 순서를 촘촘하게 연결해야 하는 목표는 하나의 workstream으로 묶는다. 각 workstream의 작업 순서와 완료 조건은 해당 workstream 안에서 확인할 수 있게 유지한다.

### 의존 관계 조회

확정: task와 workstream의 의존 관계를 트리 형태로 펼쳐 점검할 수 있게 한다. 여러 항목이 같은 선행 항목을 공유할 수 있으므로 트리의 가지와 실제 항목의 식별자를 구분한다. 반복 등장한 항목은 같은 ID의 참조로 표시한다.

다음은 조회 API 제안이다. 기본 응답은 기존 CLI 계약과 같은 JSON이며, 트리 구조의 관계와 항목별 상태를 제공한다.

| 제안 명령 | 동작 |
| --- | --- |
| `task tree TASK_ID` | 특정 task가 기다리는 선행 task들을 펼쳐 조회한다. |
| `task tree --workstream WORKSTREAM_ID` | workstream 내부 전체 task의 의존 관계를 조회한다. |
| `task workstream tree WORKSTREAM_ID` | 특정 workstream이 기다리는 선행 workstream들을 펼쳐 조회한다. |

아래는 선행 방향으로 펼친 표시 예시다. 실제 식별자와 상태 표현은 출력 스키마에서 확정한다.

```text
서비스 출시
├─ 인증 기능 완료
│  └─ 공통 기반 완료
└─ 결제 기능 완료
   └─ 공통 기반 완료 (같은 항목 참조)
```

조회에는 항목 ID·제목·현재 상태·대기 원인을 포함한다. workstream 외부의 차단 원인도 task 조회에서 확인할 수 있게 한다. 역방향 조회, 깊이 제한, 일부 결과의 이어 읽기, 사람이 읽는 텍스트 출력 옵션은 API 상세화 때 정한다.

### 점유와 실행

| 제안 명령 | 동작 |
| --- | --- |
| `task claim --workstream WORKSTREAM_ID` | 실행 가능한 작업 하나를 선택해 점유한다. |
| `task claim TASK_ID` | 특정 작업을 점유한다. |
| `task current` | 현재 worktree와 연결된 실행을 조회한다. |
| `task checkpoint RUN_ID --file FILE` | 진행 요약과 다음 행동을 저장한다. |
| `task release RUN_ID` | 작업을 이어갈 수 있도록 점유를 반납한다. |
| `task resume` | 현재 연결과 유효한 점유 증명을 확인해 같은 run을 계속한다. |
| `task resume TASK_ID` | 지정한 task의 유효한 점유 증명으로 같은 run을 계속한다. |
| `task takeover TASK_ID` | 관찰한 기존 점유를 새 run으로 명시적으로 인계받는다. |
| `task unclaim TASK_ID` | 최신 profile 리비전과 관찰한 run을 검사하여 관리 목적으로 점유를 해제한다. 사유를 기록하며 실행 프로세스의 종료는 별도로 관리한다. |
| `task done TASK_ID --file FILE` | 최종 결과와 검증 근거를 연결해 완료 처리한다. |

점유를 변경하는 요청은 실행 컨텍스트를 통해 현재 점유 증명을 확인한다. 위 예시에 공통 `--context` 또는 `DEVTOOLS_TASK_CONTEXT` 전달 규칙을 적용한다. 표시용 owner 이름과 실제 점유 권한은 구분한다.

`claim` 결과에는 task 상세, workstream 공통 맥락, 기준 명세·계획 리비전, run ID, 점유 생성 시각과 실행 컨텍스트 참조를 제공한다. 점유 증명 원문은 CLI가 보관한다. 독립 task는 자체 목표와 완료 조건을 제공한다. 기본 조회는 요약을 반환하고, 긴 명세·기록은 참조를 통해 필요한 범위를 추가로 조회하는 구성을 제안한다. 조회 결과가 일부인 경우 그 사실과 이어 읽는 방법을 표시한다.

확정: 점유는 시간 경과로 만료되지 않으며 완료·반납·명시적 인계까지 유지한다. 최근 활동 시각과 체크포인트는 복구 판단의 근거로 사용한다. 긴 빌드나 세션의 침묵을 종료 신호로 간주하지 않는다.

`resume`은 유효한 점유 증명을 가진 기존 run을 계속한다. `takeover`는 새 run을 생성하고 이전 점유 증명을 무효화한다. 종료되거나 인계된 run에 대한 checkpoint·release·done 같은 실행 변경 요청은 현재 점유 검사에서 거절한다.

같은 worktree의 연결 정보는 복구할 실행을 찾는 단서다. `current`는 조회이며 점유를 새로 부여하지 않는다. 표시용 owner 이름과 경로도 세션의 생존이나 신원을 증명하지 않는다. 같은 점유 증명을 복사해 사용하는 두 프로세스를 도구가 서로 다른 세션으로 구별할 수는 없으므로, 세션 교체에는 명시적 인계를 사용한다. 이 점유 모델은 같은 사용자 계정 안에서 에이전트의 실수와 오래된 요청을 제어하는 협업 규칙이다.

확정: `takeover`는 호출자가 관찰한 기존 run ID를 제출한다. 저장 시 현재 점유의 run ID와 일치하는 요청만 적용하고 달라졌다면 충돌을 반환한다. 두 인계 요청이 같은 실행을 대상으로 경쟁할 때 하나만 성공한다. 인계 후에는 새 run ID와 새 실행 컨텍스트를 발급한다.

### 확정: 실행 컨텍스트

CLI는 실행별 점유 증명을 사용자 전용 저장소에 보관한다. run ID는 조회용 식별자이고 실행 컨텍스트는 해당 증명을 변경 요청에 연결하는 참조다. 컨텍스트에는 profile·task·run의 연결이 있어야 하며 요청 대상과 현재 점유에 일치하는지 확인한다. 일반 조회 결과는 점유 증명을 제공하지 않는다.

호출자는 `claim` 또는 `takeover`가 반환한 컨텍스트 참조를 이후 변경 요청에 명시적으로 전달하거나, 에이전트의 명령 실행 환경에 연결한다. CLI는 그 참조로 보관된 증명을 읽고 검증한다. CLI 자식 프로세스가 부모 셸의 환경을 바꿀 수 없으므로, 환경 연결은 호출 측 스킬이나 실행 어댑터가 수행한다. 각 명령이 별도 셸에서 실행되는 환경에서도 명시적 전달로 같은 컨텍스트를 사용할 수 있게 한다.

run ID나 worktree 경로만으로 변경 권한을 자동 선택하지 않는다. 기존 실행을 계속할 때는 같은 컨텍스트를 사용하고, 새 세션은 기록을 조회한 뒤 명시적 `takeover`로 새 컨텍스트를 받는다. 컨텍스트 참조도 실행 권한에 연결되는 정보이므로 일반 작업 메모나 공유 dashboard에 게시하지 않는다.

컨텍스트를 복사한 같은 사용자 계정의 프로세스를 별도 신원으로 인증하는 모델은 아니다. 인계 시 이전 컨텍스트를 무효화해 과거 세션의 실수와 늦은 요청을 차단한다. 명시적 인계 요청은 이 사용자 계정의 복구 동작으로 처리하며, 이전 세션의 종료 여부는 호출자가 실제 환경에서 확인한다.

점유는 작업 관리 데이터의 동시 변경을 보호한다. 코드 변경은 에이전트별 worktree를 기본으로 한다. 이전 프로세스가 계속 실행될 가능성과 서로 다른 task의 파일·외부 자원 충돌은 별도로 확인한다.

### 체크포인트와 검증

체크포인트에는 완료한 내용, 중요한 결정과 이유, 검증 결과 참조, 남은 일, 다음 행동, 막힌 이유를 저장한다. 도구는 실행 ID, 기록 시각, 연결된 worktree, 기준 리비전을 함께 기록한다.

검증 결과에는 검증 항목 ID, 방법이나 명령, 결과, 실행 시각, 대상 커밋과 작업 디렉터리 변경 상태, 근거를 연결한다. 재실행 결과는 새 기록으로 보존한다. 검증 등록 API와 결과 상태는 상세 기본 계약을 따른다.

개별 task의 완료에는 해당 작업의 완료 조건과 필요한 검증 근거를 확인한다. 통합 검증은 관련 task와 연결된 별도 검증 항목으로 관리하고, workstream 마감 시 전체 목표 충족 여부를 확인한다.

### 재시도와 동시 변경

변경 요청에는 요청 식별자를 사용한다. 같은 식별자와 같은 입력의 재시도는 이전 적용 결과를 복구한다. action을 다시 적용하거나 이미 종료된 점유를 부활시키지 않는다. 과거 점유 결과가 참조하는 run과 현재 유효성을 구분하며 충돌·보존 규칙은 상세 기본 계약을 따른다.

설명·계획처럼 여러 에이전트가 수정할 수 있는 데이터에는 변경 충돌 검사를 둔다. 충돌 응답에는 최신 상태를 다시 조회할 수 있는 정보를 제공한다. 상세 기본 계약의 리비전 옵션과 오류 코드를 사용한다.

## 세션 재개와 완료 후 기록

새 세션은 `current` 또는 task 조회로 기존 실행을 찾고 목표·명세·계획·체크포인트를 읽는다. 실제 Git 변경과 남은 프로세스를 확인한 뒤 `takeover`로 새 run에 인계한다. 활동이 오래 없다는 사실은 복구 후보를 찾는 단서이며, 자동으로 점유를 해제하는 조건이 아니다.

기존 실행을 그대로 계속하는 `resume`은 같은 run과 점유 증명을 사용한다. 반납된 작업은 `claim`으로 새 run을 시작한다. 완료·취소된 작업의 재개는 해당 action의 전이 조건을 먼저 만족해야 한다. `takeover`는 점유 인계이며 완료·취소나 실행 차단 조건을 우회하는 동작으로 사용하지 않는다.

완료하면 점유를 해제하고 현재 작업 연결을 정리한다. 원본 이력의 완료 기록이 기준이며 worktree 연결 정보의 정리에 실패해도 조회 시 원본과 대조해 종료된 실행으로 표시한다. 연결을 정리할 때는 같은 run을 가리키는 연결만 처리해 새 실행의 연결을 보존한다. 최종 결과·검증·관련 커밋과 실행 이력을 보존하고, 기본 조회에는 현재 작업과 완료 요약을 중심으로 표시한다. worktree와 파일 정리는 별도 선택으로 관리한다.

## 논리 점검과 남은 계약

| 상황 | 일관성을 유지하는 규칙 |
| --- | --- |
| 동시에 같은 task를 점유 | 조건 확인과 action 기록을 원자적으로 처리해 유효한 점유 하나를 유지. |
| 같은 시각의 완료·재개 또는 시계 변경 | 적용 순번으로 이력을 계산하고 시각은 활동 기록으로 사용. |
| 긴 작업이나 세션 오류 | 점유 유지. 기록과 실제 환경 확인 후 명시적으로 인계. |
| 기존 완료 요청과 인계 요청의 경쟁 | 먼저 적용된 action을 기준으로 다음 요청의 현재 점유와 완료 조건을 재검사. |
| 두 세션의 동시 인계 | 관찰한 기존 run ID와 현재 점유의 run ID가 같을 때만 인계. |
| 인계 후 이전 세션의 변경 요청 | 이전 증명으로 실행 기록과 완료 결과를 변경하는 요청 거절. 파일 작업은 별도 확인. |
| 성공 응답 유실 후 재시도 | 같은 요청의 과거 결과를 복구하고 현재 점유 유효성을 별도로 확인. |
| 완료 후 worktree 연결 정리 실패 | 원본 이력으로 종료 여부를 판정하고 오래된 연결을 정리. |

action 이력과 명시적 인계 모델은 위의 불변 조건으로 연결된다. 구체적인 컨텍스트 전달과 실행 중 변경·취소·재개는 상세 기본 계약을 따른다.

실행 중 의존성 편집은 점유를 유지하고 영향을 받은 실행을 stale로 표시한다. 완료 이력도 유지하며 현재 유효성만 재평가한다. 명시 취소·재개에는 기존 후행 보호 제약을 적용한다.

## 확정: dashboard와 동적 조회

`devtools dashboard`는 전체 profile의 현황과 작업 관계를 탐색하고 편집하는 화면의 진입점이다. CLI가 로컬 관리 서버를 준비하고 접속 URL을 출력한다. `--json`으로 구조화된 결과를 받는다. 에이전트는 이 링크를 사용자에게 전달하고 사용자는 브라우저에서 열어볼 수 있다. 변경 요청은 [관리 API 계약](management-api-contract.md)의 리비전·재시도·관리 대상 검증을 따른다.

```sh
# 현재 프로젝트의 profile을 처음 선택하거나 전체 profile 요약으로 시작
devtools dashboard

# 지정한 profile을 처음 선택
devtools dashboard --profile myapp
```

처음 선택할 대상은 명시한 `--profile`, 현재 프로젝트에서 해석한 profile, 전체 profile 요약 순서로 정한다. 화면에서 다른 profile로 전환하거나 전체 보기를 선택할 수 있다. 처음 선택한 profile은 시작 위치이며 조회 가능한 범위를 제한하는 설정이 아니다.

### 필요한 범위만 계산

조회 서버는 요청받은 범위의 데이터를 그 시점에 계산한다. profile을 선택하면 해당 profile의 요약을, workstream을 펼치면 해당 task와 의존 관계를, 노드를 선택하면 해당 항목의 상세·실행·검증 기록을 조회한다. 전체 보기는 profile 요약을 요청하고 세부 데이터는 탐색 과정에서 요청한다.

실행 가능 여부와 대기 원인을 계산할 때는 요청 범위 밖의 선행 항목도 필요한 만큼 확인한다. 응답에는 요청한 범위와 그 결과를 이해하는 데 필요한 차단 원인을 담는다.

캐시는 조회 조건과 관련 데이터 리비전을 기준으로 재사용한다. 의존 관계에 의해 참조하는 선행 항목의 변경도 캐시 유효성에 반영한다. 응답에는 기준 리비전과 계산 시점을 제공하고, 서로 다른 시점에 조회한 화면 데이터는 기준을 구분해 표시하거나 다시 조회한다. 캐시 수명은 상세 기본 계약을 따른다.

### 그래프 화면

Canvas 기반 그래프로 profile·workstream·task의 소속과 의존성을 표시한다. 소속은 묶음 영역으로, 의존성은 선행에서 후행으로 향하는 화살표로 구분한다. 독립 task는 profile 아래에 표시한다. 전체 흐름에서 workstream을 펼쳐 내부 task를 탐색할 수 있게 한다.

그래프는 D3.js 7.9.0과 Canvas로 구현한다. 노드 상세 조회, 확대·이동, 검색, 선행·후행 경로 강조를 제공한다. 공식 배포 번들과 라이선스를 실행 파일에 포함하며 버전과 SHA-256을 함께 기록한다.

dashboard는 저장된 action 이력을 기준으로 계산된 상태를 조회한다. 조회가 점유나 작업 진행을 변경하지 않도록 한다. task 이외의 도구를 연결할 경우에도 secret 값은 HTML과 조회 응답에 포함하지 않는 기존 경계를 유지한다.

확정: dashboard는 사용자별 로컬 서버 하나를 재사용하고 명시적인 종료 명령을 제공한다. profile 전환은 같은 서버에서 처리한다. 준비 상태·동시 시작·접속·조회·초기 profile 처리는 상세 기본 계약을 따른다.

## 단일 devtools 스킬의 역할

스킬은 사용자 의도를 구체화하고 명세·계획을 작성하며, 작업을 분해하고 구현·검증 결과를 판단한다. CLI는 저장·조회·참조 검사·점유·상태 변경·기록 복구를 담당한다.

스킬의 기본 흐름은 현재 맥락 조회, 필요한 판단, 다음 행동 수행, 근거 기록이다. 에이전트별 대화 기억 대신 devtools에 저장된 작업 맥락을 재개 기준으로 사용한다.

CLI가 명령과 입력·출력 스키마를 제공하고, 스킬에는 판단 기준과 사용 흐름을 둔다. 계획의 상세도와 검증 범위는 작업의 영향에 맞춰 선택한다.

## 상세 기본 계약

### 상태와 허용 전이

task의 수명주기는 생성·재개 후 `open`, 완료 후 `done`, 취소 후 `canceled`로 계산한다. 점유 여부는 별도의 `running`과 `current_run`으로 반환한다. `ready`는 included open 또는 done+stale이고 점유·명시적 대기가 없으며 모든 선행 조건을 만족할 때 true다. `blockers`에는 미완료 선행 task, 선행 workstream, 명시적인 대기 사유를 구분해 제공한다.

workstream은 생성 후 `draft`, 실행 준비 action 후 `active`, 마감 후 `done`, 취소 후 `canceled`다. `activate`는 명세·계획·task·검증의 구조 검사를 통과해야 한다. 선행 workstream이 남아 있어도 active가 될 수 있지만 소속 task의 claim은 대기한다. 소속 task의 점유에는 workstream이 active여야 한다는 조건도 적용한다.

task의 done은 유효한 점유와 완료 결과·필수 검증 근거를 요구한다. reopen은 done 또는 canceled를 open으로 되돌리고 새 점유는 별도로 요청한다. workstream reopen은 draft로 되돌리며 소속 task를 자동으로 재개하지 않는다. 상태는 각 action 기록에서 계산한다.

| 변경 상황 | 처리 |
| --- | --- |
| 영향받는 후행 작업 시작 전 | 조건 검사 후 변경하고 실행 가능 여부 재계산. |
| 정의 편집 영향 범위에 점유가 있음 | 점유 보존, 의미 기준 변경 시 stale. 검토 후 sync로 최신 기준 연결. |
| 정의 편집 영향 범위의 후행 항목이 done | 완료 이력 보존, 의미 기준 변경 시 stale. ready이면 원자 reopen+claim. |

영향 범위는 대상과 변경 전·후 그래프의 후행 경로 합집합이다. workstream 변경은 그 경로에 속한 task와 점유까지 포함한다. 검사와 변경을 원자적으로 처리한다. 재개 대상 자신의 완료와 소속 관계로 연결된 내부 완료 기록은 의존 관계상 후행 완료와 구분한다. workstream 재개는 내부 완료 기록을 보존하며 외부 후행을 검사한다. 구체적인 영향 범위는 API 상세 계약을 따른다.

workstream task 정의는 실행 중에도 수정한다. 공통 본문은 소속 전체, 구조화된 조건은 직접 참조와 후행의 기준에 영향을 준다. 관련 없는 task 삽입·제외는 기존 task 완료를 유지한다. 명시적 대기는 hold/unhold로 설정하며 기존 점유 제약을 적용한다.

취소에는 이유를 기록한다. workstream 취소는 영향 범위의 현재 점유가 없음을 확인한 후 소속 open task 취소와 함께 적용한다. done task의 결과는 보존한다. workstream close는 included task가 current 완료 또는 canceled이고 제외 task를 포함한 현재 점유가 없으며 전체 완료 조건과 필수 통합 검증이 충족됐을 때 가능하다. 취소한 task의 완료 조건은 다른 결과 또는 명시적인 범위 변경·면제 기록으로 설명해야 한다.

task당 workstream은 최대 하나다. 연결 변경·해제는 open이고 점유가 없으며 양방향 의존 관계와 workstream 완료 조건 참조가 비어 있을 때 허용한다. 먼저 관계를 명시적으로 정리한 뒤 이동한다. 연결 대상은 같은 profile의 draft 또는 active workstream이다. 기존·새 계획의 task 참조 갱신은 연결 변경과 함께 적용한다.

### 입력·식별자·재시도

ID는 도구가 발급하는 불변 식별자이며 API는 응답의 전체 ID를 사용한다. 요구사항·완료 조건은 문서 내부의 불변 key로 참조한다. 예시로 `REQ-001`, `AC-001`을 사용할 수 있으며 workstream ID와 조합해 식별한다.

간단한 생성은 CLI 옵션, 여러 필드의 등록·수정은 `--file FILE` 또는 `--stdin`의 JSON 객체로 받는다. 파일과 stdin은 택일이다. 본문 필드와 같은 의미의 CLI 옵션을 함께 전달하면 입력 오류다. `--profile`, `--context`, `--request-id`, `--if-revision`은 호출 제어 정보로 별도 전달한다.

명세 JSON은 `body` Markdown, `requirements` 배열의 `key`·`text`, `acceptance` 배열의 `key`·`requirement_keys`·`text`를 가진다. 계획 JSON은 `body`, `task_ids`, `validation_ids`를 가진다. 처음에는 참조를 비워 작성할 수 있고 activate 전에 완성한다. task JSON은 `title`, `description`, 선택적인 `workstream_id`, 자체 완료 조건 `acceptance`, workstream 조건 참조 `acceptance_keys`를 가진다.

변경 요청은 호출자가 생성한 `--request-id`를 받는다. profile·요청 ID·정규화된 입력이 같으면 원래 결과를 복구하고, ID가 같고 입력이 다르면 충돌한다. 요청 기록은 해당 profile의 이력과 함께 보존한다. 같은 요청의 재시도는 action을 다시 적용하거나 종료된 점유를 복원하지 않는다.

문서·관계·완료 조건 수정과 취소·재개·활성화·마감·면제 요청에는 읽었던 profile 리비전을 `--if-revision`으로 제출한다. 현재 리비전이 다르면 최신 내용을 조회하여 재판단한다. 실행 변경은 현재 컨텍스트를 검사하고 인계는 `--expected-run RUN_ID`를 검사한다. action 적용 직전에 관련 조건을 모두 다시 확인한다.

### 실행 컨텍스트와 현재 연결

변경 명령은 `--context CONTEXT` 또는 `DEVTOOLS_TASK_CONTEXT`로 참조를 받으며 명시 옵션이 우선한다. 선택된 profile·task·run과 현재 점유가 일치해야 한다. 컨텍스트를 사용하는 명령도 profile은 기존 규칙대로 명시 옵션 또는 devtools.toml로 선택한다.

CLI는 전역 저장소에 정규화된 디렉터리와 run의 연결을 기록한다. Git에서는 worktree 루트, Git 밖에서는 claim의 `--dir` 또는 현재 디렉터리를 사용한다. 같은 디렉터리에 여러 run이 연결될 수 있으므로 `current`는 목록을 반환한다. 대상 없는 resume는 전달한 컨텍스트가 가리키는 실행을 사용하며, 컨텍스트가 없으면 필요한 입력을 안내한다.

takeover는 현재 점유가 있는 open task의 인계다. 완료·취소·실행 차단 조건을 다시 검사하고 이전 실행과 새 run을 연결한다. 반납된 작업은 claim으로 이어간다. 새로운 디렉터리에서 takeover하면 새 연결을 기록하고 이전 경로를 이력으로 보존한다. 일반 조회와 dashboard에는 컨텍스트 참조를 포함하지 않는다.

### 검증과 증거

validation은 `title`, `method`, `required`, 연결 대상 task 또는 workstream, 완료 조건 참조를 가진다. `validation add --file`로 등록하고 `validation record VAL_ID --file`로 실행 결과를 추가한다. 결과는 `pass`, `fail`, `blocked`, `skipped`이며 시각·명령이나 방법·근거·기준 문서 리비전·코드 상태를 기록한다. task 결과 등록은 현재 실행 컨텍스트를 사용하고 workstream 결과는 profile의 명시적인 기록 요청으로 처리한다.

필수 검증은 현재 기준에 적용 가능한 최신 결과가 pass여야 한다. 검증 기준은 profile의 현재 리비전과 구분한 basis_id로 참조한다. 검증 결과 저장이나 무관한 기록 추가는 해당 검증 근거를 무효화하지 않는다. `validation waive VAL_ID --reason TEXT`는 해당 기준에 적용할 명시적 면제 action이다. skipped 결과 자체는 면제가 아니다. task별 검증은 done 전에, 통합 검증은 workstream close 전에 확인한다. 검증 범위를 해석하고 실제 코드와 근거가 일치하는지 확인하는 책임은 에이전트에게 있다.

완료 목록은 상태 필터로 조회하고 기본 작업 목록은 open task와 draft·active workstream을 반환한다. 기록은 보존하고 기본 상세는 최종 요약을 제공한다. 전체 진행률 대신 상태별 작업 수·남은 검증·차단 원인을 제공한다.

### 보완 명령과 응답

앞의 명령 표에 다음 동작을 포함한다. 변경 명령에는 공통 요청 ID와 해당 리비전 또는 컨텍스트를 전달한다.

| 명령 | 동작 |
| --- | --- |
| `task workstream activate WS_ID` | 구조 검사 후 실행 준비. |
| `task update TASK_ID --file FILE` | workstream task는 lifecycle과 별도로 설명·완료 조건 수정. 독립 task는 기존 전이 제약 유지. |
| `task attach TASK_ID --workstream WS_ID`, `task detach TASK_ID` | 소속 연결·해제. |
| `task depends set TASK_ID --file FILE` | 선행 task 목록 교체. |
| `task workstream depends set WS_ID --file FILE` | 선행 workstream 목록 교체. |
| `task impact TASK_ID`, `task workstream impact WS_ID` | 후행 영향·현재 점유·완료 항목 조회. 변경 JSON을 전달하면 변경 후 범위도 비교. |
| `task hold TASK_ID --reason TEXT`, `task unhold TASK_ID` | 명시적 대기 설정·해제. |
| `task cancel TASK_ID --reason TEXT`, `task reopen TASK_ID --reason TEXT` | 취소·재개. workstream에도 같은 동사 제공. |
| `task history TASK_ID`, `task workstream history WS_ID` | action·인계·검증 기록 조회. |
| `task export TASK_ID`, `task workstream export WS_ID` | 해당 리비전의 본문·관계·기록을 JSON으로 내보내기. 실행 증명은 제외. |

의존성 JSON은 `{ "depends_on": ["선행 ID"] }`다. 배열 전체를 교체하며 빈 배열은 해제한다. 중복 ID는 하나로 정규화한다. 관계 검사와 영향 검사는 변경 직전에 다시 수행한다.

기존 JSON 봉투를 사용하며 data에는 `profile`, 기준 `revision`과 명령별 결과를 담는다. 변경 결과에는 적용 action과 대상, 재시도 여부를 포함한다. 자동 claim에서 ready 항목이 없으면 `claimed: false`와 이유로 성공한다. 특정 task의 조건 위반은 충돌이다. 자동 선택은 ready 항목의 생성 순번·ID 순서다.

| 종료 코드 | 오류 |
| --- | --- |
| 1 | `storage_error`, `io_error`, `dashboard_unavailable` |
| 2 | `invalid_argument` |
| 3 | `not_found`, `revision_conflict`, `request_conflict`, `claim_conflict`, `context_invalid`, `dependency_conflict`, `transition_conflict`, `validation_required`, `cursor_invalid` |
| 130 | `canceled` |

profile 해석 오류는 기존 CLI 계약을 따른다. 오류 details에는 대상과 차단·충돌 원인을 담고 점유 증명과 컨텍스트는 포함하지 않는다.

목록은 기본 50개, 최대 200개와 cursor로 조회한다. ID 순으로 정렬하고 이어 읽기는 같은 리비전의 결과를 사용한다. 스냅샷은 마지막 접근 후 30분 동안 유지하며 만료하면 새 조회를 안내한다. 트리는 `--direction upstream|downstream`과 `--depth`를 제공한다. 기본은 upstream·깊이 3, 최대 깊이는 20이다. JSON에는 `nodes`, `edges`, `roots`, 리비전을 반환하고 응답당 최대 200개 노드 이후의 가지는 이어 조회할 ID를 표시한다.

### Dashboard 수명과 접근

`devtools dashboard`는 서버가 준비되면 `url`과 시작 profile을 반환하고 종료한다. 서버는 사용자별 하나를 재사용하며 `devtools dashboard status`로 확인하고 `devtools dashboard stop`으로 종료한다. stop은 조회 세션을 무효화하며 작업·점유 이력을 유지한다. 동시 시작은 하나의 서버로 합치고 오래된 프로세스 기록은 서버의 응답과 식별자를 확인한 뒤 정리한다.

loopback의 사용 가능한 포트에 바인딩한다. 링크 fragment의 임시 접속 증명을 브라우저의 로컬 조회 세션으로 교환하고 API는 같은 origin과 세션을 검사한다. 원격 origin을 허용하지 않으며 외부 스크립트 로드 없이 화면 자원을 제공한다. 작업 본문은 텍스트 또는 안전하게 렌더링한 Markdown으로 표시한다.

명시적 profile이 유효한 이름이고 데이터가 없으면 빈 화면으로 시작한다. 현재 프로젝트 설정이 잘못됐다면 기존 해석 오류를 반환하며 명시적 profile로 시작 위치를 선택할 수 있다. 첫 선택은 조회 범위를 제한하지 않는다.

캐시는 사용자별 devtools 캐시 디렉터리에서 조건·profile 리비전·projection 버전으로 관리한다. 같은 profile의 action이 추가되면 이전 리비전 캐시는 최신 조회에 사용하지 않는다. 전체 요약은 profile별 리비전을 반환한다. 화면의 탐색·새로고침 때 최신 데이터를 요청하며 다른 리비전의 영역은 다시 조회한다. 조회 캐시는 마지막 접근 후 30분 기준으로 정리하고 원본 기록은 유지한다.

Canvas 그래프와 같은 정보를 검색 가능한 목록·상세 영역에서도 제공한다. 계층형 배치, 확대·이동·검색·선행/후행 강조를 기본으로 한다. 라이브러리와 내부 HTTP 경로는 사용자 계약과 분리된 구현 선택으로 둔다.

### 최종 논리 점검

원자적인 profile 단위 판정으로 claim·인계·관계 변경의 경쟁을 처리한다. 진행 중 정의 변경은 점유를 유지하고 영향을 받은 실행을 stale로 표시한다. 관찰 리비전과 현재 context로 sync한 후 최신 기준에서 검증한다. 완료된 후행은 이력을 보존하며 현재 기준이 달라지면 stale로 판정한다. 검증 근거와 실제 외부 파일 상태의 일치는 에이전트가 확인한다.

구현 검증에는 동시 claim·동시 takeover·done과 takeover 경쟁·성공 응답 유실·늦은 요청·여러 선행 항목·완료된 후행 재개 충돌·캐시 리비전 변경을 포함한다. 기존 Docker 샌드박스에서 Go 검사와 설치된 실행 파일의 공개 CLI 시나리오를 검증한다.

## 계약 범위 요약

| 순서 | 계약 | 기본 동작 |
| --- | --- | --- |
| 1 | 명세·계획 | Markdown 본문과 구조화된 참조를 JSON으로 함께 등록하고 리비전 충돌 검사. |
| 2 | 상태·소속·의존성 | action 기반 계산, 같은 범위의 복수 선행 조건, 상시 정의 편집과 current/stale 분리, 완료 이력 보존. |
| 3 | 점유·복구 | 만료 없는 점유, 명시적 실행 컨텍스트, 기존 run을 검사한 새 run 인계. |
| 4 | 변경·재시도 | profile 리비전과 요청 ID로 동시 수정·중복 적용 제어. |
| 5 | 검증·마감 | task별 검증과 workstream 통합 검증, 명시적 면제와 근거 기반 마감. |
| 6 | 스킬 통합 | 현재 맥락 조회부터 인계·완료까지 단일 devtools 스킬로 안내. |
| 7 | dashboard | 사용자별 로컬 서버, 상태·종료 명령, 세션 접근 제어, 리비전 캐시와 동적 Canvas 조회. |

구현 시 이 계약을 명령 스키마와 성공·오류·동시성·복구 테스트에 반영한다.
